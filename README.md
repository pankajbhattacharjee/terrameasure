# TerraMeasure — Geospatial File Measurement API

I built this as a submission for the Aereo engineering
assignment. The goal was straightforward: accept a
geospatial file, figure out what's in it, and return
real measurements in metres — not degrees, not
approximations.

It turned out to be a deeper problem than I expected,
mostly because of CRS. That rabbit hole is documented
below.

---

## What it does

Upload a Shapefile (.zip) or KML file. The API reads
every feature inside it, works out the coordinate
system, projects the geometry into metres, and returns
area (for polygons) and length (for lines). Points are
flagged as unsupported — they never crash the request.

| Geometry type      | What you get                              |
| ------------------ | ----------------------------------------- |
| Polygon            | area in m²                                |
| MultiPolygon       | area in m² (holes subtracted correctly)   |
| LineString         | length in m                               |
| MultiLineString    | length in m (all segments summed)         |
| Point / MultiPoint | flagged, no measurement, request succeeds |
| GeometryCollection | measured if all members are supported     |

Every measurable feature also gets a WGS 84 geodesic
value alongside the planar one, so you can spot-check
the numbers without trusting the projection math blind.

---

## Stack

* **FastAPI** — the backend framework (as required)
* **pyshp** — reads Shapefile binary format
* **pyproj** — CRS transforms and geodesic measurements
* **Shapely** — geometry operations (area, length)
* **SQLAlchemy + PostgreSQL** — stores files and features
* **Python's stdlib** — zipfile for .zip, ElementTree
  for KML (no heavy dependencies)

There is also a lightweight Next.js dashboard at `/`
that wraps the API with an upload form and a
measurements table — but the Python service is the
real backend. Every endpoint works with plain `curl`.

## Setup

You need Python ≥ 3.10 and PostgreSQL.

```bash
# Clone the repo
git clone https://github.com/pankajbhattacharjee/terrameasure
cd terrameasure

# Install Python dependencies
pip install -r backend/requirements.txt

# Set your database URL
cp .env.example .env
# Edit .env → DATABASE_URL=postgresql://user:pass@localhost/dbname

# Run the API
cd backend
uvicorn app:app --reload
# API →  http://127.0.0.1:8000
# Docs → http://127.0.0.1:8000/docs  (auto-generated by FastAPI)
```

Tables are created automatically on startup. No migrations needed for the initial schema.

### File-processing flow

**1. Transport** FastAPI validates the file extension and size (50 MB cap) before touching any file content. Bad extensions get a 415 before any parsing work starts.

**2. Decode**

* KML → Python's stdlib ElementTree walks every **`<Placemark>`** at any nesting depth. Attributes come from **`<name>`**, **`<description>`**, and **`<ExtendedData>`**. Geometries are built as Shapely objects directly.
* ZIP → stdlib zipfile enumerates entries. Each **`.shp`** layer is opened with pyshp; shapes are converted to Shapely via **`__geo_interface__`**. Multi-layer zips are flattened into one list with a **`layer`** attribute so no data is silently dropped. A zip containing only a **`.kml`** is handled gracefully.
* **`.prj`** sidecars are read for CRS resolution.

**3. CRS resolution** KML is always EPSG:4326 by spec. For Shapefiles, the **`.prj`** WKT is parsed:

* EPSG code recovered from **`AUTHORITY[...]`** strings
* Geographic files inferred from WGS 84 / NAD83 names
* UTM zones derived from Transverse Mercator central meridian math (scale factor 0.9996)
* **`UNIT[...]`** factor captured for US survey foot files
* Missing **`.prj`** → assumed EPSG:4326, flagged in note

**4. Measurement** See below.

**5. Persistence** File record + all features committed in a single SQLAlchemy transaction. Either everything saves or nothing does.

### Measurement calculation flow

**`measure_feature()`** is a pure function — it never raises an exception. Here is what happens:

**Geographic CRS (EPSG:4326 or any lon-lat system)** A representative point is taken from the geometry and used to pick the right UTM zone: **`zone = floor((lon + 180) / 6) + 1`** North → EPSG:326xx, South → EPSG:327xx

The geometry is projected into that zone with **`pyproj.Transformer`** (**`always_xy=True`** — this caught a real bug during development), then area and length are computed from the projected Shapely geometry.

**No math is done in degrees.**

**Projected CRS** Area and length are computed directly in the source CRS, then multiplied by the unit factor from the WKT so the result is always in metres.

**Always — geodesic cross-check** The geometry is also measured with **`pyproj.Geod(ellps="WGS84")`** using **`geometry_area_perimeter`** and **`geometry_length`**. This gives an independent ellipsoidal reference that typically agrees with the UTM planar value to within ≈ 0.5 % for normal survey-sized features.

**Unsupported types** Points, empty geometries, and unknown types return **`supported: false`** with a human-readable note. The request still returns 200 — one unsupported feature does not kill the whole file.

### CRS handling summary

| **Source**             | **Detected as**     | **Measured in**          |
| ---------------------- | ------------------- | ------------------------ |
| KML                    | EPSG:4326 (by spec) | Per-feature UTM zone     |
| Shapefile with .prj    | WKT → EPSG code     | Source CRS or UTM        |
| Shapefile without .prj | Assumed EPSG:4326   | Per-feature UTM, flagged |

## Design decisions

**FastAPI over Django** FastAPI's async-ready design, native Pydantic validation, and auto-generated OpenAPI docs made it a better fit for a stateless file-processing service than Django's ORM-first structure.

**Synchronous processing on upload** For files under 50 MB, the whole pipeline (parse → CRS → measure → persist) runs in under a second on normal survey files. Adding an async queue would just add latency with no real benefit at this scale. The **`status`** field is already in the schema, so moving heavy processing to a Celery/RQ worker later is a drop-in change — not a schema migration.

**Per-feature UTM instead of one fixed projection** Web Mercator (EPSG:3857) distorts area badly at high latitudes. A single equal-area projection like EPSG:6933 is better, but per-feature UTM keeps local distortion below ≈ 0.1 % for any reasonably sized feature. Surveyors use UTM for exactly this reason.

**Geodesic cross-check alongside planar** The requirement says to transform before measuring, not to use geodesic-only. But reporting two independent numbers turns "is this right?" from a trust question into a comparison. If they diverge by more than ≈ 0.5 %, something in the projection pipeline is wrong and it shows immediately.

**pyshp + pyproj + Shapely over GDAL** Pure-Python wheels — no system GDAL library needed, no binary compilation, trivial to deploy anywhere Python runs. The three libraries together cover parsing, CRS transforms, and geometry math.

**JSONB for geometries instead of PostGIS** No spatial queries, spatial indexes, or overlay operations are needed for this workflow. Storing raw GeoJSON means the API serialization is zero-mapping. PostGIS would be the right upgrade if the service ever needed queries like "find all features within this bounding box."

**Multi-layer Shapefile zips — flatten, don't drop** If a zip contains three **`.shp`** layers, silently taking only the first one loses data. All layers are flattened into one feature list with a **`layer`** property so the consumer can still tell them apart and nothing is silently discarded.

## What I learned

CRS is a data problem, not a library problem.

The edge cases are not in the area or length math — those are two or three lines of code. The edge cases are WKT files without **`AUTHORITY`** strings, coordinate order surprises that **`always_xy=True`** fixes, KML producers that use nonstandard namespace URIs, and US-survey-foot Shapefiles where the WKT **`UNIT`** factor is 0.3048006... not 0.3048.

Building the test fixtures by hand — writing the .shp/.dbf bytes with analytically known geometries rather than downloading a real-world file — was the right call. It gave me a regression suite where I know the correct answer before I run the test.

Reporting two independent measurements (planar + geodesic) removes the "is this number right?" question entirely. It is either within 0.5 % or it is not.

## Future scope

* **Async task queue** — Celery or RQ for files above the synchronous ceiling. The **`status`** column already supports PROCESSING → COMPLETED/FAILED transitions.
* **PostGIS** — store geometry as **`GEOGRAPHY`**, use **`ST_Area`** / **`ST_Length`** / **`ST_Transform`** as an authoritative server-side cross-check.
* **More formats** — GDAL/OGR bindings would add GeoPackage, GeoJSON, GML, and proper NTv2/NADCON datum grid support.
* **Export** — download measurements as GeoJSON or CSV for use in GIS tools.
* **Streaming progress** — Server-Sent Events for per-feature progress on very large files.
